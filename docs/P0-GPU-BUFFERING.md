# P0-GPU-BUFFERING: configurable CPU and GPU presentation

## Scope and commands

This experiment introduces two independent parameters:

| Option | Values | Default | Description |
| --- | --- | --- | --- |
| `--renderer` / `ASTER_RENDERER` | `cpu`, `gpu`, `auto` | `cpu` | Select CPU OSR, GPU shared-texture OSR, or an attempted GPU path with CPU fallback. |
| `--buffers` / `ASTER_BUFFERS` | `1`, `2` | `1` | Number of presentation buffers per tab, for either renderer. |

The CLI parameters override environment values. `--renderer gpu` requires the `cef-gpu` Cargo feature, which includes `cef` and the experimental Slint WGPU 30 renderer. `--renderer auto` is only meaningful when the binary is built with `cef-gpu`. A normal CEF-only build uses the tested CPU path. The optional `ASTER_GPU_POWER=high|low` changes WGPU adapter power preference (default high); it does *not* guarantee matching CEF's GPU.

```sh
cargo test -p browser-contracts
cargo test -p browser-core
cargo test -p frontend-slint
cargo test -p engine-cef --features cef-runtime
cargo check -p aster-desktop --features cef
# Additional toolchain, Vulkan and CEF SDK dependencies apply:
cargo test -p browser-render-wgpu
cargo check -p aster-desktop --features cef-gpu

ASTER_PERF=1 cargo run --release -p aster-desktop --features cef -- --renderer cpu --buffers 1
ASTER_PERF=1 cargo run --release -p aster-desktop --features cef -- --renderer cpu --buffers 2
ASTER_PERF=1 cargo run --release -p aster-desktop --features cef-gpu -- --renderer gpu --buffers 1
ASTER_PERF=1 cargo run --release -p aster-desktop --features cef-gpu -- --renderer gpu --buffers 2
ASTER_PERF=1 cargo run --release -p aster-desktop --features cef-gpu -- --renderer auto --buffers 2
```

## CPU renderer

A ring of 1 or 2 shared RGB pixel buffers receives the BGRA dirty patches generated by CEF's incremental CPU framebuffer. In two-buffer mode, each inactive buffer replays the patches since its last presentation before it is displayed again, preventing stale pixels. A full frame or resize reinitializes both slots. Slint may still perform copy-on-write when holding a previous image; two buffers improve *opportunities* for reuse but do not guarantee zero-copy.

## Accelerated GPU renderer

1. Slint selects the WGPU 30/Vulkan renderer and provides its **own** `wgpu::Device` and `wgpu::Queue` through its rendering notifier.
2. CEF creates a windowless browser with `shared_texture_enabled` and supplies `OnAcceleratedPaint` frames. On Linux, this means imported DMA-BUF handles. The native CEF callback's borrowed handle is used only while the callback is valid.
3. The upstream `cef-rs` importer copies the shared resource into an **owned GPU texture** and waits for completion before returning. This remains a complete GPU-to-GPU copy; it does not read back the texture to CPU memory.
4. Aster renders only the damage rectangles into one or two persistent RGBA8 presentation textures with a WGPU shader and scissor rectangles. The shader also converts CEF BGRA8 output to Slint-compatible RGBA8 without CPU readback. An inactive texture accumulates any missed damage until it is selected.
5. Slint imports the GPU presentation texture via `slint::Image::try_from(wgpu::Texture)`, using the **same** WGPU device and queue. GPU queue ordering ensures that the shader passes are submitted before the UI samples their textures. Unlike the CPU path there is no per-frame BGRA-to-RGB conversion.

This path **does not claim absolute zero-copy**. The full upstream GPU import/copy remains, followed by GPU shader writes limited to the damage regions. No persistent CEF shared-image handle is retained, and no GPU work is submitted from background threads. The experimental GPU path is built only when explicitly requested.

## Fallback and lifecycle

- The frontend and engine share a neutral WGPU bridge crate. `browser-contracts` and `browser-core` have no CEF, Slint or WGPU dependency.
- A GPU browser is created after Slint announces WGPU device setup. Tab open/navigation/resize requests are queued during initialization.
- If importing or presenting a GPU frame fails, or an active GPU browser provides no frame for eight seconds, the engine closes GPU browsers, waits for their `OnBeforeClose` acknowledgements, then recreates them as CPU OSR browsers. URLs and viewport sizes are preserved. In-page state (e.g. form content, scroll offset) is **not** preserved across this fallback.
- Full compositor/window init failures may prevent the UI from starting. In that situation re-run with `--renderer cpu`; do not disable Chromium's sandbox.
- GPU accelerated OSR is hardware and driver dependent. Under Linux hybrid graphics, a mismatch between the GPU chosen by Chromium and the GPU chosen by Slint can cause DMA-BUF import failure. This is a supported fallback scenario, not permission to disable security features.
- NVIDIA/CEF 156 has had an upstream DMA-BUF synchronization regression. Keep your CEF binary and graphics drivers updated, validate repeated resizing and avoid claiming a driver is safe solely based on compilation.

## Instrumentation

With `ASTER_PERF=1`, look at:

- `[aster:cef]` — CPU paint, dirty-rect compare and copies.
- `[aster:slint]` — CPU converted pixels, frame cadence and frontend pump duration.
- `[aster:gpu]` — frames/s, upstream complete GPU import-copy volume, estimated Aster presentation write volume, full and partial regions, and CPU submission time.
- `[aster:pump]` — scheduled versus fallback CEF message loop work.

The GPU byte counters are estimates from uncompressed texture dimensions and regions, **not** actual hardware memory bandwidth or GPU timing queries. `submission_cpu_avg` excludes the `cef-rs` importer's blocking wait. Do not compare GPU and CPU copies as though they measured the same bus.

## Manual acceptance gate (Linux/KDE Wayland)

- [ ] Both CPU buffer counts compile and render identical pixels after intermittent dirty updates and resizes.
- [ ] Navigation, keyboard, mouse, scrolling, tab switching and shutdown work in both CPU modes.
- [ ] `cef-gpu` builds using the same WGPU 30 crate version as `cef-rs` and Slint.
- [ ] GPU mode renders `tests/manual/damage.html` without any full CPU readback.
- [ ] GPU mode with one and two buffers renders identical pixels; verify alternating frames and updates to inactive tabs.
- [ ] GPU partial-region write metrics are below full-frame copy metrics for small animations.
- [ ] Simulate unsupported GPU import and confirm that tabs reappear using CPU OSR without a hang.
- [ ] Check GPU device/driver compatibility, resizing, suspend/resume and shutdown on the actual machine.
- [ ] A/B compare frame pacing and memory at fixed OSR frame rates, with CPU vs GPU and 1 vs 2 buffers.

**No GPU performance or correctness claim is validated until the above run on the target system.**
